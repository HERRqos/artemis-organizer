# Next step: same bot as a web chatbot widget

Goal: reuse the existing engine (LLM + tools + calendar + escalation) behind a
new web-facing entry point, instead of WhatsApp, for a chat widget on a site
(e.g. next to the "new episode" banner).

## Reuse as-is, no changes needed

- `services/engine/app/conversation.py` — `Conversation.run()` only needs
  `user_text` + `history` + `ToolContext`. Doesn't know WhatsApp exists.
- `services/engine/app/tools/` — calendar tools, unchanged.
- `services/engine/app/llm.py`, `prompts.py` — unchanged.
- `services/engine/app/escalation.py` — keyword gate still applies as-is.
- `shared/assistant_shared/calendar.py` — same `CalendarService`.

## Needs modification

- `services/engine/app/session.py` (`SessionStore`) — currently keys
  conversation memory by WhatsApp phone number (`sender`). A web visitor has
  no phone number — needs a different identity, e.g. a browser session
  id/cookie generated by the widget.
- `shared/assistant_shared/models.py` (`InboundMessage`) — `channel` field
  would need a new value (`"web"`), `sender` becomes that session id instead
  of a `wa_id`.

## New files to create

- A new service, mirroring `services/webhook/`'s split:
  - something like `services/webchat/app/main.py` — the HTTP/websocket
    endpoint the browser widget talks to.
  - `services/webchat/app/core.py` — pure logic version (no FastAPI types),
    same pattern as `webhook/app/core.py`.
  - own `Dockerfile`, own `requirements.txt`.
- A reply path for the web: WhatsApp's send step (`whatsapp.py`) doesn't
  apply — for web chat the reply can likely just be returned directly in the
  HTTP/websocket response, no separate "send" client needed.
- The actual chat widget itself (HTML/JS) — front-end, lives on the website,
  not in this Python backend.
- `docker-compose.yml` — add a service entry for the new `webchat` container.
- `.env.example` — any new env vars this endpoint needs (e.g. CORS allowed
  origins, session cookie secret).

## Decision: synchronous, no queue

Chose simpler synchronous request/response over the async queue pattern.
No Redis stream needed for this path — the webchat endpoint calls
`Conversation.run()` directly and returns the reply in the same
HTTP/websocket response. Simpler because there's no Meta-retry pressure to
answer instantly; the browser is just waiting for its reply anyway.

Implication to remember: the tool-calling loop (LLM + calendar calls) can
take a few seconds, especially across multiple tool rounds — the endpoint
needs a long-enough request timeout (and the widget should show a "typing…"
state) instead of assuming a near-instant reply like a normal REST call.
